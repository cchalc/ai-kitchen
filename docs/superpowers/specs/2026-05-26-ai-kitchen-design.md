# ai-kitchen — Repository Setup Design

**Status:** Design (pending user approval)
**Date:** 2026-05-26
**Author:** Christopher Chalcraft (with Claude)

## Purpose

`ai-kitchen` is a personal incubator for Databricks Field Engineering skills, slash commands, agents, and supporting tools. Skills are drafted in `scratch/`, promoted to `plugin/` when mature, and published to the official Vibe marketplace (`databricks/vibe`) via `/vibe-publish-plugin` when ready to share. The repo is single-author (cchalc / christopher-chalcraft_data) and private.

## Goals

- One repo holds *both* a publishable Vibe plugin and a freeform scratchpad for WIP ideas, without mixing the two.
- `/vibe-publish-plugin` works against `plugin/` with zero adaptation — the directory is a valid Vibe plugin from day one.
- Python tooling (uv-managed) coexists with the plugin without polluting it.
- `jj` is the primary local VCS; `git` exists only for GitHub interop.
- `wt` (worktrunk) can be used for parallel skill work; venvs do not multiply per worktree.
- A new Claude session in this directory can orient itself in under 60 seconds by reading `CLAUDE.md` + `checkpoint.md`.

## Non-goals

- A marketplace (multi-plugin) layout. If a second plugin is ever needed, the repo will be restructured then; for now there is exactly one plugin.
- General-purpose Python packaging (no wheel build). `pyproject.toml` uses `tool.uv.package = false`.
- Cross-platform Windows support. macOS + Linux only.
- Replacing the user's existing global Claude config at `~/.claude/`.

## Approach

**Selected: Approach C — Plugin in subdir, Python at root.**

Rejected alternatives:
- **Approach A (plugin at repo root)** — Mixes plugin metadata with Python/scratch metadata at the same level. Makes `/vibe-publish-plugin` slightly easier (no `cd plugin/`) but blurs the boundary between "what publishes" and "what doesn't."
- **Approach B (marketplace + multiple plugins)** — Useful only if multiple distinct plugins are planned. Premature for a one-person catalog; carries marketplace.json + per-plugin CODEOWNERS overhead.

## Python: devenv + uv (dual path)

The repo supports two ways to enter a Python development shell. devenv is preferred; bare direnv+uv is the fallback for hosts without Nix/devenv.

**`.envrc`:**

```sh
# Path 1 (preferred): devenv — Nix-reproducible shell with uv inside.
if has devenv && [ -f devenv.nix ]; then
  use devenv
  return
fi

# Path 2 (fallback): plain direnv + uv per the cchalc gist.
# Requires: direnv + uv on PATH.
export UV_PROJECT_ENVIRONMENT="$HOME/.virtualenvs/ai-kitchen"
```

**`devenv.nix`:**

```nix
{ pkgs, ... }: {
  languages.python.enable = true;
  languages.python.package = pkgs.python311;
  languages.python.uv.enable = true;

  enterShell = ''
    export UV_PROJECT_ENVIRONMENT="$HOME/.virtualenvs/ai-kitchen"
    if [ ! -d "$UV_PROJECT_ENVIRONMENT" ]; then
      uv sync
    fi
  '';
}
```

**`devenv.yaml`:**

```yaml
inputs:
  nixpkgs:
    url: github:cachix/devenv-nixpkgs/rolling
```

**`pyproject.toml`:**

```toml
[project]
name = "ai-kitchen"
version = "0.1.0"
description = "Personal Databricks FE skills and tools (incubator)"
requires-python = ">=3.11"
dependencies = []

[tool.uv]
package = false
```

**Venv path is hardcoded** to `~/.virtualenvs/ai-kitchen` so `wt` worktrees (which have different basenames like `feature-x`) all share one venv. The trade-off: renaming the repo directory requires editing one line in `.envrc` and `devenv.nix`.

## VCS: jj colocated + worktrunk

**One-time jj setup** (run after files are created, from inside the repo):
```sh
jj git init --colocate
```

This adds `.jj/` alongside the existing `.git/`. `.gitignore` is honored by jj in colocated mode; no `.jjignore` is created.

**Day-to-day:**
- `jj new` → start a working change
- `jj describe -m "..."` → set message
- `jj git push` → push to GitHub
- `jj bookmark create <name>` / `jj bookmark move <name>` → manage branches

**`wt` (worktrunk):** No `.config/wt.toml` in v1. Defaults are fine. If hook automation is needed later, suggested first hook is `post-start` running `direnv allow` so the venv loads in a fresh worktree.

## Living documentation

Four root-level Markdown files updated *during* work, distinct from formal specs.

| File | Updater | Cadence | Read order |
|------|---------|---------|-----------|
| `README.md` | You / Claude | When public facts change | First on GitHub |
| `CLAUDE.md` | You / Claude | When conventions evolve | First in a session |
| `architecture.md` | You / Claude | When a structural decision is revisited | When designing changes |
| `tasks.md` | Claude (mostly) | Every session | Session start |
| `lessons.md` | Claude (mostly) | When something non-obvious surfaces; append-only | When stuck |
| `checkpoint.md` | Claude (mostly) | Session end; overwritten | Session start |

CLAUDE.md instructs Claude to: read `checkpoint.md` and `tasks.md` at session start; append to `lessons.md` on surprises; overwrite `checkpoint.md` at session end.

## CLAUDE.md content

Final content for `CLAUDE.md`:

```markdown
# ai-kitchen

Personal incubator for Databricks Field Engineering skills and tools.
Mature work graduates to the official vibe marketplace via
`/vibe-publish-plugin`. Anything in `scratch/` is WIP and not for general use.

## Repo layout
- `plugin/`   — publishable Vibe plugin (canonical layout)
- `scratch/`  — drafts; not published; rename to `plugin/skills/<name>` when ready
- `tools/`    — Python helpers; share the root uv venv
- `docs/`     — design specs (incl. `docs/superpowers/specs/`)

## Living docs (read these in order at session start)
1. `checkpoint.md` — where I left off
2. `tasks.md` — in-progress + next
3. `lessons.md` — append-only learnings (consult when stuck)
4. `architecture.md` — why things are shaped this way

At session end: overwrite `checkpoint.md` with current state.
On surprises: append a dated entry to `lessons.md`.

## Conventions
- Skills live under `plugin/skills/<kebab-name>/SKILL.md`.
- Skill `description` MUST include "when to use" + explicit negative
  triggers (vibe CI requires ≥95% routing accuracy).
- `skill-routing.yaml` evals: max 2 entries per skill (vibe CI hard limit).
- Shell snippets must be Linux-compatible. Forbidden on Linux CI:
  `sed -i ''`, `base64 -i`, `stat -f`, `date -v`, `/Applications/...`.

## VCS
- `jj` is the primary local VCS; colocated with git.
- `git` exists for GitHub interop only. Use `jj git push` to publish.
- `wt` (worktrunk) for parallel skill work. Default config; no `.config/wt.toml`.

## Python
- Single venv at `~/.virtualenvs/ai-kitchen` (shared across worktrees).
- `direnv allow` once; the shell auto-loads the env on `cd`.
- Two entry paths supported: `devenv.nix` (preferred) or plain `uv` fallback.
- `uv add <pkg>` to add deps. `uv run python tools/x.py` to run scripts.
- Footnote: if you rename the repo dir, update the hardcoded path in
  `.envrc` and `devenv.nix` (`enterShell`).

## Promotion workflow
1. Draft in `scratch/<idea>/`.
2. Validate skill: kebab-case `name`, "when to use" + negative triggers
   in `description`, Linux-safe shell.
3. `git mv scratch/<idea> plugin/skills/<idea>` (jj sees the rename).
4. `cd plugin && /vibe-publish-plugin` — auto-detects, dupe-checks,
   validates, opens PR to `databricks/vibe`.

## Safety
- Never run `/vibe-publish-plugin` from `scratch/` — it's intentionally
  outside the plugin and won't be detected.
- Don't commit credentials. `.gitignore` covers `.env*`; double-check.
```

## Promotion workflow (canonical sequence)

```sh
# 1. Draft
jj new
mkdir -p scratch/my-new-skill
$EDITOR scratch/my-new-skill/SKILL.md
jj describe -m "draft: my-new-skill"

# 2. Validate (manual)
#    - frontmatter: name (kebab-case), description (when-to-use + negative triggers)
#    - shell snippets Linux-safe

# 3. Promote
jj new
git mv scratch/my-new-skill plugin/skills/my-new-skill
jj describe -m "promote: my-new-skill"

# 4. Publish
cd plugin
/vibe-publish-plugin
```
